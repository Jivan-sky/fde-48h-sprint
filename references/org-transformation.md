# 组织变革层：human–agent 组织如何接进 ANC

> 用途：P 轨道与路线 B 的 Phase 0 / 2 / 5 / 6 / 7 / 8 / 11。
> 来源：McKinsey & Company, *AI is changing work. Now it has to change the organization*, 2026-10。这里只吸收组织设计概念，不复述原文。
> 一句话：**麦肯锡补「组织怎么变」，ANC 补「运行时怎么落」；两边用 mission 接起来。**

## 先校准，别把麦肯锡当成 0 中层蓝图

- 麦肯锡讲的是 **human–agent organization**，不是「0 中层公司」；它明确保留 accountable leader、业务负责人和控制职能。
- 它没有承诺「永久中层归零」；它只论证中层作为信息路由层和默认职业终点的理由在缩小。
- 4-6 人 hybrid team 是某一家公司的案例信号，不是普遍标准。
- 调查数字（个人提效高、组织准备度低、重塑阶段比例低）是诊断语言，不是因果保证。
- 它不提供 Context/Skills/Agent/Evals 的实现，也不替客户解决 DRI 授权、法律责任和审计。

因此：**不要把 P 轨道包装成「麦肯锡认证的 0 中层」；也不要把「0 中层」当成裁员方案对外说。**

## 五件套：把组织变革变成可交付物

| 组件 | 要回答什么 | 产出 | 接进哪个 Phase |
|---|---|---|---|
| **Mission charter** | 哪个业务结果值得做？基线、目标、预算、约束、停止条件、谁对结果负责？ | 一页 mission charter | Phase 0/2/6 |
| **Orchestration chart** | 围绕这个结果，哪些人/agent 一起工作？谁做什么？哪些交接消失？人在哪里保留判断和责任？ | as-is / to-be 编排图 + 决策权图 | Phase 5/7 |
| **Mission factory** | 谁组成跨职能交付单元？业务、技术、产品、数据、风险、法务、HR 怎么一起工作？控制怎么内置？ | mission pod + 交付节奏 + 复用资产清单 | Phase 7/10 |
| **Mission P&L / 生产力红利** | 省下的产能去哪？少用人、做更多、转更高价值、还是重组角色？成本和风险是多少？ | mission P&L + 红利去向决策 | Phase 6/7/11 |
| **Talent & trust** | 新人怎么成长为专家？技能怎么相邻迁移？职业路径是什么？员工为什么相信组织？ | 学徒阶梯 + 技能地图 + 信任计划 | Phase 8/11 |

## 角色与决策权：DRI 不是项目经理

角色可以合并，但权限不能含糊。小企业里老板可以同时是 sponsor 和 mission DRI；记录时仍要把「业务结果签字」与「日常交付协调」分开，避免 DRI 退化成新的协调层。

| 角色 | 回答什么 | 不应该做什么 | 证据 |
|---|---|---|---|
| **Sponsor / accountable leader** | 业务结果、预算、优先级、跨部门权衡；最终为结果担责 | 不代替一线定义流程；不代替 builder 做技术决定 | mission charter 签字、资源承诺 |
| **Mission DRI** | 对一条 mission 的端到端结果负责；拉通节点、例外、验收和升级 | 不是只催进度的项目经理；不默认拥有无限资源；不成为新中层 | DRI 授权页：范围/预算/否决/升级路径 |
| **Process owner / operator** | 定义 as-is/to-be 流程、例外规则、SLA 和运行责任 | 不把 AI 当责任转移对象；不签自己无法运行的东西 | 流程证据、SLA、运行记录 |
| **Builder / FDE** | 把规则、workflow、Skill、Agent、connector、eval 建出来，为生产而建 | 不替代业务负责人定义价值；不私自扩范围；不绕过控制 | 计划书、执行书、eval、runbook |
| **Coach / capability lead** | 培养判断力、学徒阶梯、技能相邻迁移、复盘和同伴学习 | 不派活、不占永久编制、不把培训出勤当 adoption | 学徒计划、技能地图、复盘记录 |
| **Control roles（I/S/R/O/Aud）** | 权限、风险、合规、发布、运行、审计 | 不在最后补签；不在信息不全时背书 | 控制点、签字、审计证据 |

最小角色集：S 轨道至少写清 sponsor、process owner、builder；P 轨道再加 mission DRI、coach 和控制角色。**角色合并可以，权力冲突不可以**（例如同一人既定义验收又独自批准上线，必须写补偿控制）。

## 组织变革六问（P 轨道必答）

1. **谁对结果负责，而且真的能调动资金、人才和优先级？** 只有头衔没有资源，不是 accountable leader。
2. **哪些工作交给 agent，哪些判断必须留给人？** 不是「AI 能做什么」，而是「出错时谁承担、什么必须可解释」。
3. **哪些交接会消失，哪些决策权必须重新写清？** 交接消失不等于责任消失；决策权图要单独画。
4. **AI 释放的产能去哪？** 少用人、做更多、转更高价值、重组角色，必须选一个并写进账。
5. **新人怎么变成专家？** 如果 AI 吃掉初级工作，学徒阶梯是什么？没有答案，两三年后能力断代。
6. **员工为什么相信组织？** 角色变化、裁员、监督、再培训，哪些说清楚、哪些有过渡？信任不是软话题，是采纳条件。

## 怎么接进现有 Phase

### Phase 0：先定 mission，不先定工具

- 老板的愿景是方向，不是需求文档；把它翻译成 1-3 个可证伪的 mission。
- 确认 accountable leader：能决定流程、数据、预算、跨部门协作的人。
- 选 S/P 轨道；P 轨道必须确认客户接受 E0 证据包，而不是 48h 原型。
- 问组织变革意愿：能不能动流程？能不能调整角色？谁会被影响？谁有一票否决？

### Phase 2：采矿时同时采「工作怎么流动」

- 除了三张清单和问题模型，补一份 **mission inventory**：候选结果、负责人、基线、价值、频率、数据、风险。
- 画当前价值链，不画全公司组织图。
- 标出「协调者角色」和「会议」：哪些只是信息传递，哪些承担判断、承诺和信任。

### Phase 5：流程图升级为 orchestration chart

现状图至少多画四层：

1. 工作步骤与角色；
2. 人/agent 分工；
3. 交接与决策权；
4. 控制点与 eval 点。

目标图要回答：哪些交接消失、哪些角色变宽、哪些判断必须留人、哪些控制不能删。

### Phase 6：把组织约束和经济账一起收敛

- 组织约束进三区表：哪些角色不能动、哪些部门必须参与、哪些审批链不能绕。
- 算 mission P&L：基线、收益、控制成本、运行成本、人工复核、异常处理。
- 明确生产力红利去向，不能只写「提效」。
- 识别「新的中层」风险：mission portfolio 管理、DRI 分配、coach 派活，都可能重新长成协调层。

### Phase 7：计划书补 P 轨道增量

P 轨道计划书除 §0-§13 外，至少补：

- mission charter；
- 价值链与 orchestration chart；
- 任务清单 + 自主性阶梯；
- pipeline 架构与例外队列；
- 48 个工作日 WBS；
- mission P&L 与红利去向；
- 组织影响图、人才/信任计划；
- 复用资产清单（skill、agent、connector、eval、模板）。

### Phase 8：和一号位谈「组织承接」，不只谈功能

- 先讲业务结果、基线、停止条件，再讲技术。
- 明确谁进 mission pod、谁处理例外、谁做最终裁决。
- 把「会不会裁员/怎么过渡/怎么培训」摆到桌面上；回避会损失信任。
- 让老板确认：如果试点有效，组织上准备改什么；如果无效，怎么停。

### Phase 11：沉淀的不只是代码

- 沉淀 skill、agent、connector、eval、编排模板和例外处理经验；
- 更新学徒阶梯、技能相邻性地图、职业路径和 coach 机制；
- 记录哪些角色变宽、哪些交接消失、哪些控制仍必须保留；
- 把 mission P&L 和红利去向写进复盘，不只写「省了多少工时」。

## Mission factory 的边界

Mission factory 是**临时/组合式交付容器**，不是新的永久中层：

- 围绕一个 mission 组建，结束后解散或重组；
- 成员来自业务、技术、产品、数据、风险、法务、HR，不另造一个庞大部门；
- 控制内置，不从外面最后补；
- 为生产而建，不为试点而建；
- 每个 mission 留下可复用资产，否则下一单从零开始；
- 如果 factory 开始长期占编制、管日常派活、拥有永久预算，它就已经变成新的中层，要重新设计。

## Pipeline 的五条原则

1. **流程先于组织**：先价值流，后角色映射，最后才谈组织架构。
2. **Pipeline 不是超级终端**：一人一 bot 是接口层；agent 嵌在流程节点上，不是让一个全能 agent 包打天下。
3. **AI at the edge，deterministic core**：AI 抽取/分类/草拟/建议；规则校验/计算/权限；人做不可逆判断。
4. **稳定核心 + 例外队列**：系统承接稳定段，业务承接例外；例外必须有队列、owner、SLA 和反馈。
5. **最小充分自主性**：规则 → 工作流 → Skill → Agent → 人工，逐任务选最低复杂度。见 `autonomy-ladder.md`。

## 反模式

- 把「0 中层」当裁员方案或对外卖点；
- 先画组织架构图，再让流程迁就部门；
- 把麦肯锡当确定性蓝图，或把 4-6 人团队当标准；
- 只做流程梳理，不画决策权和编排图；
- 只算省工时，不决定生产力红利去向；
- 不回答学徒阶梯和信任问题；
- 让 mission factory 变成新的永久中层；
- 借 P 轨道做通用平台/中台/低代码底座。

## 自检

- 这个 mission 的 accountable leader 能调动钱、人和优先级吗？
- orchestration chart 有没有画清人/agent 分工、交接、判断和控制点？
- mission factory 是临时的，还是已经变成新中层？
- 生产力红利去了哪里？谁做的决定？
- 新人怎么成长为专家？员工为什么相信这次变化？
- 哪些角色会变宽、哪些交接会消失、哪些控制不能删？
