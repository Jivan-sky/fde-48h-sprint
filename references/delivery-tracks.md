# 交付轨道：S 48h Sprint / P 48 工作日 Pipeline

> Phase 0 先选轨道。轨道与「路线 A/B（FDE / ANC）」和「部署模式 D0/D1/D2」正交，三者不能混成一个选择。
> 一句话：**S 轨道用 48h 证明一个薄切片；P 轨道用 48 个工作日把一条业务线的端到端流程做成可运行 pipeline。P 轨道默认不在 48h 交软件原型，但必须交 E0 流程证据包。**

## 两条轨道

| | S 轨道（个人/切片入口） | P 轨道（流程/业务线入口） |
|---|---|---|
| 客户信号 | 一个痛点、一个动作、愿意先看小切片 | 老板有愿景、预算、两个月决心，愿意动流程 |
| 默认范围 | 一个任务、一个用户、一个指标 | 一条业务线、一条端到端价值链、3-10 个真实用户 |
| 48h 产出 | F1/M0 可运行薄切片 | **E0 流程证据包（非软件原型）** |
| 后续 | M1 深度开发 → M2 灰度 → M3 生产 | 第 3-6 周分批建设 → 第 7-8 周试点 → 交接/生产 |
| 主要风险 | 切片有价值但无法扩展 | 梳理太久、做成大而全平台、组织不接 |
| 不能声称 | 生产可用 | 48h 已证明业务价值；或 48 天已改造全公司 |

## 选择规则

选 S：

- 需求真伪未定，先用最小切片换证据；
- 只有一个明确动作，不跨多个角色/系统；
- 客户还没有两个月预算，或不愿先动流程；
- 一线可以当场验证，失败也能快速停。

选 P：

- 老板能给出真实愿景、预算、数据访问和跨部门协调；
- 问题是跨角色、跨系统的端到端流程，不是单点工具；
- 客户要的是业务线改造，不是再买一个 agent；
- 客户接受「先 E0 证据包，再决定是否建设」；
- 有可用的真实用户、真实单据和流程 owner。

两者都像时：先用 S 打一个高风险子切片，或把 S 放进 P 的第 3-6 周作为一次 F1；**不要把 P 的默认起点写成 48h 原型。**

## E0 流程证据包（48h，不写软件）

P 轨道启动后的 48h 不是交付原型，而是交付判断依据：

1. 一条端到端价值链图（as-is）：步骤、角色、系统、输入/输出、周期、错误、返工、例外；
2. 20 个真实案例（或客户批准的脱敏样本），标明来源与日期；
3. 当前基线：周期、成本、质量、错误率、返工、吞吐；
4. 任务清单：每一步谁做、用什么系统、哪里需要判断、哪里是例外；
5. 自主性阶梯：规则 / 工作流 / Skill / Agent / 纯人工，逐任务给理由；
6. 前三个候选 mission，按价值 × 频率 × 数据可得性 × 可逆性 × 组织准备度排序；
7. 数据、权限、接口、审计、回滚缺口；
8. 48 个工作日实施草案、sponsor / mission DRI / process owner / builder 的双方责任人、停止条件和需要老板拍板的事项。

**E0 不是价值验证，也不是 F1。** 它证明「我们理解了这条流程、知道该先打哪一段」；价值验证仍要在 M1/M2 的真实使用中发生。

## 48 个工作日的节奏

| 时间 | 做什么 | 主要产出 |
|---|---|---|
| 第 1 周 | 老板对齐愿景/约束/预算；选业务线；做 E0 证据包 | 价值链图、基线、任务清单、候选 mission |
| 第 2 周 | 目标流程、自主性阶梯、pipeline 架构、数据/权限契约、mission P&L | 目标编排图、48 天 WBS、验收标准 |
| 第 3-6 周 | 按稳定段/不确定段/例外段分批建设；接系统；建异常队列；真实用户试用 | 每两周一个可用切片、eval、失败清单 |
| 第 7-8 周 | 真实案例试点；测质量/周期/成本/采纳；补监控、回滚、runbook | 试点报告、交接包、扩/改/停建议 |
| 最后几天 | 交接、培训、治理安排、资产沉淀 | runbook、owner、下一阶段计划 |

口径：**48 个工作日约 9-10 周；两个自然月约 40-44 个工作日。** 合同写「工作日」，不要只写「两个月」。

## P 轨道的五条设计原则

1. **流程先于组织。** 先画价值流，再把角色映射到流程，最后才谈组织架构；先画 org chart 会把现有部门边界固化。
2. **Pipeline 不是超级终端。** 一人一 bot 是接口层；公司的主干是流程。Agent 应该嵌在流程节点上，不是让一个全能 agent 包打天下。
3. **AI at the edge，deterministic core。** AI 负责抽取、分类、草拟、建议；规则负责校验、计算、权限；人负责不可逆和高价值判断。
4. **稳定核心 + 例外队列。** 系统承接稳定部分；业务承接例外判断；例外必须有队列、责任人、SLA、升级路径和反馈闭环。
5. **最小充分自主性。** 能规则就规则，能工作流就工作流，能 Skill 就 Skill，只有多步、工具、异常、非结构化输入同时存在时才上 Agent。见 `autonomy-ladder.md`。

## Pipeline 的组成

| 组成 | 要回答什么 | 证据 |
|---|---|---|
| 流程节点 | 这一步谁做、输入什么、输出什么、多久、错在哪 | 真实案例/单据 |
| 节点 agent/skill | 这一段为什么需要 AI，而不是规则/人工 | 自主性阶梯 |
| 编排器 | 状态、路由、重试、回滚由谁控制 | 流程图/状态机 |
| 交接契约 | 上游给下游什么字段、什么质量、什么异常 | schema/样例 |
| 例外队列 | 谁处理、多久处理、怎么升级 | 队列/SLA/日志 |
| 可观测性 | 每段周期、错误、成本、人工介入率 | 看板/日志 |
| 数据与权限 | 数据从哪来、能到哪、谁能看/写 | 数据分级/权限矩阵 |
| 分级 eval | 每个节点怎么判断合格 | golden set/验收标准 |

**P 轨道仍然受反平台铁律约束**：只做一条业务线的端到端流程，不借机做通用流程平台、中台、低代码底座或全公司管理系统。

## P 轨道交付物

- `计划书.md`：§0-§13 + P 轨道增量（mission charter、价值链、任务清单、pipeline 架构、48 天 WBS、mission P&L、组织/人才影响）；
- `流程证据包.md`：E0 的 8 项证据；
- `编排图.md`：as-is / to-be，人和 agent 的分工、交接、判断点、控制点；
- `角色与决策权.md`：sponsor/accountable leader、mission DRI、process owner、builder、coach、控制角色；角色合并时写清权力冲突和补偿控制；
- `mission-P&L.md`：基线、收益、成本、生产力红利去向；
- `eval/`：20 个真实案例和每阶段验收标准；
- `runbook.md`：运行、监控、告警、人工兜底、回滚、交接。

## 反模式

- 一上来梳理全公司流程，48 小时变成 48 天访谈；
- 先画组织架构图，再让流程迁就部门；
- 48 天不做任何早期证据，最后一次性交付；
- 把一条 pipeline 做成一个全能 agent；
- 让 AI 直接做确定性计算、审批或不可逆动作；
- 把例外全部丢给业务，不建队列/SLA/反馈；
- 借 P 轨道做通用平台/中台/低代码底座；
- 把 E0 当价值验证，或把 48h 原型当 P 轨道默认起点；
- 只算省工时，不算控制/运行成本，也不决定生产力红利去哪。

## 自检

- 选的是 S 还是 P？为什么？
- P 轨道有没有在 48h 交 E0，而不是硬做原型？
- 价值链是一条业务线，还是全公司？
- 每个任务都过了自主性阶梯吗？
- DRI 是在对结果负责，还是已经变成新的项目经理/协调层？
- 例外有没有队列、owner、SLA 和反馈？
- 有没有把 pipeline 做成超级终端或通用平台？
- 48 天里有没有每两周可用的证据，而不是最后一次性交付？
