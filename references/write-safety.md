# 写入安全:先快照,后写入;先演练,后生产

> Phase 9/10 与 D1/D2 用。
> 一句话:**没有基线快照、没有回滚演练、没有审批的写入,不叫交付,叫赌博。**

**判定权威**：写入是否放行，只以 `references/phase-checklist.md` 的 25 项写入闸门卡为准；`references/write-gate-record.md` 是每次写入必须留痕的记录模板；本文件负责设计与执行方法。三者不得互相替代，也不得只挑其中一套执行。

## 适用范围

任何会改变客户系统状态的动作,都适用本文件:

- 数据库:`INSERT`/`UPDATE`/`DELETE`/`MERGE`,以及 `CREATE`/`ALTER`/`DROP`/`TRUNCATE`;
- 配置:开关、参数、字典、枚举、工作流、发布状态、显示列、版本;
- 权限:账号、角色、授权、黑名单、白名单、密钥、Token、SSO 映射;
- 文件:覆盖、移动、删除、批量导入、导出后回写;
- AI 制品:模型、Prompt、RAG 语料/索引/embedding、评测集、阈值;
- 外部副作用:消息、通知、审批、支付、退款、转账、下单、发货。

## 先分级:写的是什么环境、什么风险

| 场景 | 最低控制 | 不能省 |
|---|---|---|
| **M0 / D0-D1 演示** | 不写客户系统;必须写时改只读、一次性沙盒或人工桥 | 一次性沙盒要有重置/清理证据;共享测试环境按生产控制 |
| **M1 / D1 测试环境写入** | `write-gate-record.md` + 影响范围 + 可重置数据或快照 + 回滚/清理 + read-back | 测试环境不是法外之地;不能因为“坏了可以重装”就裸写 |
| **M2 / D2 灰度写入** | 变更单 + 写入门卡 + 灰度范围/指标/回滚/kill switch + 独立 read-back | 不得边灰度边改未评审内容;不得无 owner 值班 |
| **M3-M4 / D2 生产写入** | 变更审批 + 四眼/SoD + 完整快照/回滚/台账 + 生产写账号最小权限 | 不得绕过变更;不得个人终端直连;不得 Agent 自批自回滚 |

**写入门卡**:每次写客户系统前填 `references/write-gate-record.md`。没有这张卡,不进入执行;执行后把卡与证据一起归档。写入门卡不是“审批单替代品”,客户变更单/工单号必须回填到卡上。

**M0 铁律**:M0 只证明价值,不证明写入能力。M0 需要写才能演示的,一律改只读/一次性沙盒/人工桥;写路径留到 M1。

## 写入执行顺序(与门禁配套,不单独构成放行)

> 下面 12 步是执行顺序，不是第二套门禁。任何一步失败，仍回到 25 项闸门卡对应项判定；不能用“我这步做了”替代门禁证据。

| # | 步骤 | 产出 | 失败时 |
|---|---|---|---|
| 1 | 定义目标对象与影响范围 | 对象、数量、租户/店铺/环境、上下游 | 范围不清 → 停 |
| 2 | 只读盘点 | 数量、ID、版本、关键字段、哈希 | 拿不到 → 停 |
| 3 | 保存基线快照 | 备份/导出/事务快照 + 路径 + 哈希 | 快照不可读 → 停 |
| 4 | 定义回滚对象与回滚粒度 | 数据、配置、权限、文件、模型/Prompt/索引；行级补偿/全表恢复/PITR | 对象或粒度缺失 → 停 |
| 5 | 回滚演练 | 在影子环境恢复并核对 | 未演练 → 不得称可回滚 |
| 6 | dry-run | 影响行数、变更预览、差异清单 | 差异不符 → 停 |
| 7 | 审批 | 变更单/工单、四眼、SoD、操作人/复核人 | 未批 → 停 |
| 8 | 幂等与限额 | 幂等键、批次上限、限流、超时、kill switch | 缺失 → 不写 |
| 9 | 小批量执行 | 首批 1 条/1 个对象/1 个租户 | 异常 → 回滚 |
| 10 | read-back 校验 | 写后数量、关键字段、哈希、状态机 | 不符 → 回滚 |
| 11 | 写后快照 | 新数量/哈希/版本/审计记录 | 缺失 → 按未完成/事故处理,不得补造证据 |
| 12 | 证据台账 | 谁/何时/什么/前后值/审批号/回滚结果 | 缺失 → 不算完成;写后补证不得掩盖已发生的变化 |

## 写前闸门(与 25 项写入卡配套)

以下任一条不成立,**不写**:

1. **快照与写入故障域隔离**:快照不能只放在被写入的同一个库/同一块盘/同一台主机;至少一份在独立存储、只读或不可变介质上,并记录 URI 与哈希。
2. **快照可恢复**:不是“文件存在”,而是在影子环境实际恢复并核对数量/关键字段/哈希;没演练过,不得称可回滚。
3. **快照保留期覆盖回滚窗口**:回滚窗口结束前不得删除快照;删除快照需要独立审批。
4. **台账可用且 fail-closed**:操作台账不可写、不可查、无法关联 `operation_id` → 不执行写入;不得先写业务再补台账。
5. **操作人/复核人/审批人分离**:Agent 不得自批、自发、自审;生产写至少四眼,执行者与复核者不能是同一人;发布人按客户 SoD 与开发/执行人分离。
6. **并发互斥**:同一对象/同一批次必须有锁或写入窗口;两个 Agent/两个人不得同时写同一范围。
7. **kill switch 已演练**:不是“配置里有开关”,而是实际验证过能停止后续批次;无法停止 → 不写。
8. **回滚也是写操作**:回滚需要同样的审批、台账、read-back 和证据;紧急回滚按预先批准的 runbook 执行,不能由 Agent 临场自创。
9. **写入窗口明确**:开始/结束时间、冻结窗口、失败停止条件、通知对象;超出窗口停止。
10. **最小对象集**:只写目标对象,不顺手修关联数据;关联对象必须单独列入影响范围与回滚对象。
11. **Schema/迁移版本已核对**:目标库当前 schema、迁移版本、对象定义、约束、触发器和应用版本一致;存在未合并迁移、未知触发器或版本漂移 → 不写。
12. **快照本身受控**:快照按客户数据分级加密/脱敏,记录访问人、访问方式、保留期和删除审批;快照不能成为新的数据泄露源,也不能放在个人盘/个人云。
13. **回滚粒度已选对**:默认按 `operation_id` 做行级补偿;全表/分区/PITR 恢复必须冻结并发写入、盘点快照后的合法写入并有重放/补偿方案;拿不到 → 不写。

## 回滚粒度:先补偿,后恢复(快照不是默认回滚方式)

**快照回答“原来是什么”,不等于“可以直接覆盖回去”。** 在共享库/生产库上直接 restore 一张表,会把快照之后别人的正常写入一起抹掉,造成第二次事故(丢失更新)。

| 回滚方式 | 适用 | 必须满足 | 主要风险 |
|---|---|---|---|
| **行级补偿(默认)** | 能按 `operation_id` + 对象键定位本次写入的对象 | 有写前 before-image/字段值;补偿只作用于本次对象;带幂等键 | 关联表、触发器、缓存/索引、外部副作用要单独补偿 |
| **全表/分区恢复** | 本次写入覆盖表的大部分,或行级补偿不可行 | 冻结该表所有写入;证明无并发合法写入;盘点并重放快照后的合法变更;独立审批 | 覆盖快照后的正常业务写入 |
| **PITR/整库恢复** | 灾难恢复,不是单批次回滚 | 事故指挥、影响范围、恢复点、重放清单、业务停服窗口 | 代价最高;不得用来“撤销一次误操作” |

硬规则:

1. **默认先做行级补偿**;只有行级补偿不可行,才升级到全表/分区恢复。
2. 全表/分区/PITR 恢复前,必须盘点快照时间点之后的**所有合法写入**,并有重放/补偿方案;拿不到 → 不恢复,按事故升级。
3. **恢复前先保存当前状态**(快照/导出/日志);否则回滚会毁掉现场证据。
4. 回滚顺序:停止后续批次 → 冻结对象 → 保存当前状态 → 行级补偿/恢复 → read-back → 解冻 → 复盘。
5. **共享生产库禁止“直接 restore 一张表”作为常规回滚**;这是第二次事故的高发点。
6. 回滚后核对:目标对象、关联表、序列、审计、缓存/索引、外部副作用。

### 行级补偿的最小数据单元:before-image 与对象键映射

`operation_id` 不是客户业务表天然存在的字段。若目标表没有、客户也不批准增加 `operation_id` 列，执行 Agent **不得假设“按 operation_id 一查就能回滚”**。每次写入前必须在受控台账里登记“本次写了哪些对象、对象主键是什么、变更前值在哪里、补偿动作是什么”，才能做行级补偿。

| 变更类型 | 写前必须保存 | 默认补偿动作 | 不得直接补偿的情形 |
|---|---|---|---|
| `INSERT` | 生成的业务主键/唯一键、完整写入值、批次 ID | 按**精确主键**逐条删除本次插入对象；先确认无后续业务引用 | 已被下游引用、已触发外部消息/审批/计费；改为标记/冲正/人工处置 |
| `UPDATE` | 被更新对象的完整 before-image（至少覆盖所有被写字段与版本/更新时间）、对象主键 | 按主键用 before-image 恢复；带版本/时间条件防止覆盖后续并发写 | 目标行已被别人再修改；先保存当前值并判断是否可安全补偿 |
| `DELETE` | 被删除行的完整 before-image、主键、序列/自增值、关联关系 | 按原主键 reinsert，并核对唯一键、外键、序列、软删除标记 | 删除已触发级联、外部通知、审计确认或下游清理；升级为恢复/人工处置 |

规则：

1. **before-image 正文放受控加密存储，台账只放 URI、SHA-256、主键和字段清单**；不得把完整业务行、个人信息或凭据复制进操作台账。
2. **对象键必须可复现**：记录 schema/表、主键列、主键值（必要时复合键）和租户/环境；只有对象 ID 清单、没有定位规则，不算可补偿。
3. **补偿前先重读当前值**：若当前值已不等于本次写入后的值，说明存在后续并发写；停止自动补偿，保存当前状态并升级。
4. **新增与删除都要列出级联/触发器/外部副作用**；不能只删主表一行就宣称回滚完成。
5. **批量写入必须逐对象或逐批记录映射**；只记录“批次共 N 条”不足以保证精确补偿。

### 数据库写入附加检查(命中任一项,先停)

1. **约束与外键**:写前列出目标表的主键/唯一键、非空、检查约束、外键和级联规则;确认写入不会把关联表置空、孤儿化或触发非预期级联。
2. **触发器与计算列**:列出 `BEFORE`/`AFTER` 触发器、审计触发器、计算列和物化视图刷新;不能只看目标表的最终行数。
3. **事务隔离与锁**:记录隔离级别、锁范围、锁等待上限和长事务检测;禁止在未知锁策略下做跨表大事务。
4. **死锁与重试**:死锁/序列化失败只允许带幂等键做有限重试;重试不得重复产生业务效果;超过预算停止并升级。
5. **迁移与回滚版本**:记录应用版本、schema 版本、迁移 ID、回滚迁移 ID;写入前后版本必须匹配,禁止用临时 SQL 绕过迁移工具。
6. **写后关联核对**:read-back 除目标表外,还要核对触发器/级联影响到的关联表、审计表、搜索索引和缓存;发现额外变化即按失败处理。
7. **快照一致性**:多表/多对象快照必须来自同一事务一致性视图或同一 PITR 时间点;记录 LSN/GTID/binlog position/快照时间。各表各自导出、时间不一致 → 不得作为联合回滚基线。
8. **read-back 读源**:写后校验必须读主库,或确认副本已追平并记录复制延迟;不得用滞后副本、缓存或搜索索引的旧值判断写入成功。
9. **read-back 独立性**:read-back 必须用独立查询/独立连接/独立凭证,不能复用写接口的返回、缓存或 ORM 会话中的旧对象;写接口返回成功 ≠ 数据已落对。
10. **序列与自增**:回滚对象包含自增 ID/序列/版本号/时间戳/软删除标记;只回数据行不回序列,会造成后续主键冲突或外部引用错位。回滚后必须核对序列当前值与最大 ID。
11. **事务边界与部分成功**:跨表/跨服务写入必须定义事务边界、失败补偿或 outbox;禁止把一个业务动作拆成多个无关联事务后把“部分成功”当成功。外部消息只能在业务事务提交后发,或走可重试的 outbox。
12. **写账号最小权限**:生产写账号只授予目标 schema/表/动作,禁止 DDL、跨库、批量删除和 `GRANT`;写账号与读账号、审计账号分离;凭证不得由执行 Agent 长期持有。

## 操作台账(operation journal)

写前快照和回滚脚本只证明「理论上能恢复」;操作台账证明「这一次到底做了什么、能不能追到人、出错时回滚到哪」。任何 D1/D2 写入都必须有台账,且台账本身受控、追加写、不可由执行 Agent 删除。

| 字段 | 内容 |
|---|---|
| `operation_id` | 全局唯一;与变更单、日志、批次、证据文件同一 ID |
| `idempotency_key` | 防重复执行;重试不得生成第二个业务效果 |
| `目标与范围` | 环境/租户/店铺/表/对象 ID/数量/上下游 |
| `写前基线` | 数量、ID 清单/范围、版本、关键字段哈希、快照 URI |
| `快照保护` | 分级、加密、访问人、保留期、删除审批 |
| `审批与职责` | 变更号、审批人、操作人、复核人、SoD 结论 |
| `dry-run` | 影响行数/差异清单/预期对象与实际对象 |
| `执行` | 批次 ID、起止时间、结果、失败重试、kill switch 状态 |
| `写后校验` | read-back 数量、关键字段、状态机、关联表/触发器/级联影响、哈希、审计记录 |
| `回滚` | 触发条件、回滚对象、执行人、结果、回滚后哈希、验证人 |
| `证据` | 日志/截图/导出文件 URI、哈希、保留位置 |

规则:

1. **台账先于业务写入**:先写 `operation_id` 与「准备中」记录,再执行;不能等写完才补。
2. **追加写**:禁止覆盖或删除历史记录;更正用新记录 + 关联原 ID。
3. **最小化**:台账只存对象 ID、哈希、URI 和结论,不复制行级业务数据、凭据或完整请求体。
4. **独立可查**:客户审计/运行角色可按 `operation_id` 追到变更单、快照、日志和回滚记录。
5. **失败也记录**:中止、回滚、部分成功都必须落状态,不能只留成功记录。
6. **保留期**:按客户政策;项目结束移交 owner,不留在 FDE 个人设备。
7. **fail-closed**:台账存储不可用、写入失败或读回不一致 → 停止业务写入,不得降级为“只记日志”。
8. **状态机完整**:`prepared → approved → executing → succeeded / failed / rolled_back`;任何状态跳变都视为异常。
9. **防篡改**:台账用追加写、独立凭据、只写权限或 WORM/哈希链;执行 Agent 不得拥有删除/改历史权限。
10. **时间源一致**:时间戳来自客户受控时钟/NTP;跨系统对账时记录时区与时钟偏差。
11. **operation_id 由受控系统生成**:不得由执行 Agent 随手编;与变更单、批次、日志、证据文件同一 ID。
12. **部分成功 = 失败**:停止后续批次,先对账、再决定回滚;不得用“大部分成功”结案。

### 台账与快照落库(最小结构示例)

字段名按客户规范调整;关键是**业务写入前先落 prepared 记录**,且执行 Agent 没有删除/改历史权限。

| 表/对象 | 关键字段 | 约束 |
|---|---|---|
| `operation_journal` | `operation_id` PK、变更号、环境、对象范围、状态、审批人/操作人/复核人、开始/结束时间、kill switch 状态、结论 | 追加写;状态机 `prepared → approved → executing → succeeded / failed / rolled_back`;按 `operation_id` 可检索 |
| `operation_snapshot` | `snapshot_id` PK、`operation_id` FK、对象类型、对象键、版本/LSN/GTID、SHA-256、快照 URI、保留期、访问人 | 快照正文放受控存储;台账只存 URI/哈希/元数据,不复制行级业务数据 |
| `operation_change_item` | `operation_id` + `item_no` 复合主键、对象类型、主键/对象键、变更类型 `INSERT/UPDATE/DELETE`、before-image URI、写后哈希/版本、补偿动作、当前状态 | 每条被写对象都要有映射;补偿前重读当前值;状态 `planned → written → compensated / compensation_blocked` |
| `operation_rollback_step` | `operation_id` + `step_no` 复合主键、目标、动作、前置条件、验证方式、执行人、结果、回滚后哈希 | 回滚步骤预先审批;执行结果逐条回读;不得临场自创 |

> 若客户已有变更/审计平台,把这三类记录映射进去即可;不要为了“自建台账”绕开客户既有控制。

## 数据库写入

### 硬规则

1. **DDL 与 DML 分开**:DDL 必须单独变更单、单独窗口、单独回滚方案;探索阶段永远不执行 DDL。
2. **写前必须有可恢复备份**:逻辑备份/物理快照/事务日志,三者至少一种,并确认可读。
3. **更新/删除必须有 `WHERE`**:禁止无 `WHERE` 的 `UPDATE`/`DELETE`;禁止 `WHERE 1=1`。
4. **先 `SELECT` 同条件**:确认影响行数与对象清单,再执行写。
5. **事务 + 批次上限**:能事务就事务;不能事务就分批,每批可回滚。
6. **写后 read-back**:行数、关键字段、状态、关联表、哈希,至少四项。
7. **恢复演练**:备份不是回滚;能在影子库恢复并核对,才算回滚能力。
8. **生产写入必须有审计**:binlog/审计日志/变更记录,保留期按客户政策。
9. **优先软删除/版本化**:能软删除就不硬删除;硬删除必须单独审批、单独窗口、单独回滚。
10. **禁止无边界批量**:`DELETE`/`UPDATE` 必须有精确 `WHERE`、批次上限和 `ORDER BY`/主键范围;禁止 `WHERE 1=1`、全表、无主键范围。
11. **使用客户批准的变更工具**:优先 migration/change tool/受控 runbook;临时 SQL 必须审批、留档、复核,不得从 FDE 个人终端直连生产。
12. **写后对账跨对象**:目标表之外,还要核对关联表、缓存、搜索索引、权限矩阵和外部副作用;只核对目标表不算完成。

### 店铺初始化示例(只读基线 → 写入 → 回读)

1. 写前读取:模型列表、品类树、套餐列表、价格、状态、版本号;
2. 记录:每类数量、ID 清单、名称/编码、版本/更新时间、关键字段哈希;
3. 导出:JSON/CSV 快照到客户受控目录,记录路径与 SHA-256;
4. 写入:按对象分批,每批带幂等键,记录批次 ID;
5. 回读:数量、ID、名称、价格、状态、关联关系逐项比对;
6. 不符:停止后续批次,按快照回滚,核对回滚后哈希;
7. 证据:写前/写后快照、差异、审批号、操作人/复核人、回滚结果。

> 这不是「多此一举」。这是把「写错了怎么办」从现场反应变成事前能力。

## 配置 / 权限 / 文件 / AI 制品

| 对象 | 写前基线 | 回滚方式 | 额外要求 |
|---|---|---|---|
| 配置 | 导出当前配置 + 版本 + 哈希 | 导入旧版本/开关回退 | 差异清单、生效范围、缓存刷新 |
| 权限 | 导出角色-权限矩阵 + 账号清单 | 恢复旧矩阵/回收授权 | SoD、最小权限、生效延迟 |
| 文件 | 复制 + 哈希 + 版本 | 恢复副本/版本历史 | 覆盖前确认目标路径、禁止通配符删除 |
| 模型 | 模型名/版本/端点/参数 | 切回旧版本/旧端点 | 版本锁定、灰度、评测 |
| Prompt | Prompt 版本 + 哈希 | 回退旧版本 | golden set、输出校验 |
| RAG 索引 | 语料版本 + embedding 版本 + 索引快照 | 重建/回滚索引 | 召回评测、漂移监控 |
| 外部消息 | 模板、收件人范围、发送批次 | 撤回(如支持)/补发更正 | 先小批量、可 kill switch |

## 灰度发布

灰度不是「小范围写一点」,是**受控暴露**。必须写清:

| 项 | 必须回答 |
|---|---|
| 进入条件 | UAT 通过?控制验收通过?回滚演练通过? |
| 范围 | 哪些用户/租户/店铺/数据/流量?白名单还是百分比? |
| 观察窗口 | 多久?谁看?看哪些指标? |
| 成功判据 | 业务成功率、错误率、延迟、成本、人工复核差异 |
| 回滚触发 | 错误率阈值、数据差异、投诉、审计异常、模型漂移 |
| 回滚决策人 | 谁有权停?谁有权回滚?多长时间内决定? |
| 沟通 | 谁知道?怎么通知?对外口径? |
| 证据 | 灰度记录、指标、回滚记录、复盘 |

**灰度期间禁止**:扩大范围未经审批、绕过 feature flag、直接改生产 Prompt/模型、无 owner 值班。

## 回滚卡(每次写入前填)

| 项 | 内容 |
|---|---|
| 触发条件 | 什么指标/现象触发回滚 |
| 决策人 | 谁拍板回滚 |
| 回滚步骤 | 按顺序,可执行,含命令/入口 |
| 数据核对 | 回滚后核对哪些数量/字段/哈希 |
| 恢复验证 | 在哪个环境验证,谁验证 |
| 通知对象 | 业务/IT/安全/审计 |
| 预计耗时 | RTO |
| 证据 | 回滚记录、截图、日志、审批号 |

**回滚触发后的动作顺序**:停止后续批次 → 冻结对象/写入窗口 → 保留现场 → 通知 owner/审计 → 按 runbook 回滚 → read-back + 哈希核对 → 在影子环境复核 → 复盘与再审批。回滚失败时不得继续尝试“补写”,按事故升级。

## 反模式(命中即停)

1. 「先写一点试试」。
2. 「有备份就行」——备份没恢复过,等于没有。
3. 「回滚脚本写好了」——没跑过,不算。
4. 「生产当测试」。
5. 无 `WHERE` 的更新/删除。
6. Agent 自动放行写操作。
7. 灰度没有退出判据。
8. 只回滚代码,不回滚数据/配置/索引。
9. 回滚后不核对数据。
10. 把「客户口头同意」当变更审批。
11. 写前不读基线,写完才发现对象不对。
12. 用「再写一次」掩盖第一次的错误。
13. 快照和被写对象在同一块盘/同一个库,写完一起坏。
14. 台账不可写还继续写业务。
15. Agent 自批、自审、自回滚。
16. 回滚只回代码,不回数据/配置/权限/索引/外部消息。
17. kill switch 从未演练。
18. 两个批次并发写同一对象。
19. 把“部分成功”当成功结案。
20. 用临时 SQL 从个人终端直连生产。
21. 不核对 schema/迁移版本就写库，应用与数据库版本漂移。
22. 不知道外键/触发器/级联会把哪些关联表一起改。
23. 死锁重试不带幂等键，第一次其实已部分成功。
24. 长事务锁住核心表，写入窗口内没有锁等待上限。
25. 把「恢复快照」当默认回滚，直接 restore 一张表，覆盖快照之后的合法写入。
26. 回滚不先保存当前状态，把现场证据一起毁掉。
27. 行级补偿能解决，却直接上 PITR/整库恢复。
28. 假设业务表天然有 `operation_id`，却没有对象键映射和 before-image，就声称能行级回滚。
29. 只保存整表快照，不保存被更新/删除对象的 before-image，回滚时无法精确恢复单条记录。

## 写入演练脚本(未执行时只能标「未演练」)

以店铺初始化为例,按顺序演练并留证:

1. **只读基线**:读取模型列表、品类树、套餐/价格、权限矩阵、状态与版本号;记录数量、ID 清单、关键字段哈希。
2. **快照**:导出到独立受控存储,记录 URI、SHA-256、加密/访问人/保留期;在影子环境恢复并核对。
3. **dry-run**:只预览,不写;输出影响对象数、差异清单、预期与实际对比。
4. **审批**:变更单、四眼、SoD、写入窗口、kill switch、回滚决策人。
5. **小批量**:首批 1 个对象/1 个租户;记录 `operation_id`、幂等键、批次 ID。
6. **read-back**:数量、ID、名称/编码、价格、状态、关联关系、哈希逐项核对;同时核对外键/触发器/级联影响到的关联表、审计表、搜索索引和缓存。
7. **失败注入**:在影子环境模拟中途失败,验证停止、回滚、read-back 和证据链。
8. **回滚**:执行回滚 runbook,核对回滚后哈希;确认外部副作用是否可撤回。
9. **复盘**:记录实际耗时、发现的问题、残余风险、下次改进。

> 演练没做,就只能说“设计了回滚”,不能说“可回滚”。

## 自检

- 写前快照存在、可读、有哈希?
- 回滚对象完整(数据/配置/权限/文件/模型/Prompt/索引)?
- 回滚在影子环境演练过?
- dry-run 影响行数与预期一致?
- 审批/四眼/SoD 完成?
- 幂等键、批次上限、限流、kill switch 就位?
- 首批小批量 + read-back 通过?
- 写后快照与证据台账完整?
- schema/迁移版本、外键/触发器/级联、隔离级别与锁策略已核对?
- 死锁重试带幂等键且预算有限;read-back 已覆盖关联表/索引/缓存?
- 回滚默认是行级补偿?全表/分区/PITR 恢复是否已冻结写入、盘点并重放快照后的合法变更?
- 每个被写对象是否有主键/对象键映射和 before-image URI?新增/更新/删除的补偿动作是否分别定义?
- 灰度有进入/退出/回滚判据和 owner?
- 探索阶段写操作为 0?
