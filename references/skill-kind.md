# 制品定性:元技能 / 工作流 skill / 工具脚本 / SOP 文档

> Phase 9 用。每个产出物必须定性,定性决定它怎么封装、怎么复用(铁律「约束下沉 + 制品定性」)。
>
> **D1/D2 追加**:定性不只定「是什么」,还定「在哪个部署模式交付」。同一工具脚本,D0 是一个 `.py`;D2 还要运行手册、回滚、监控、证据。

## 四种制品

| 制品 | 定义 | 判定问题 | 封装形态 |
|---|---|---|---|
| 元技能 skill | 教 Agent「怎么判断/怎么取舍」 | 有决策分支吗?有铁律和判别程序吗? | SKILL.md(铁律+阶段+回退)+ references 判别清单 |
| 工作流 skill | 固定 SOP 固化成可复用流程 | 步骤可枚举吗?确定性高吗? | SKILL.md(线性阶段+状态文件)+ scripts/ |
| 工具脚本 | 单点自动化,无决策 | 是不是只有一个动作、零判断? | 一个脚本 + 输入输出约定 |
| SOP 文档 | 给人按步执行 | 是不是给人用、无人值守? | 步骤表(见 sop-workflow.md) |

## 判定流程(按顺序问)

1. 产物里有**判断/取舍**吗?(辨真伪、分约束、定口径)→ 有 → **元技能**成分。
2. 剩下的是**固定流程**吗?(步骤可枚举、输入输出确定)→ 是 → **工作流 skill**。
3. 只是**一个动作**的自动化?→ **工具脚本**。
4. 要**人**来执行?→ **SOP 文档**。

常见组合:一个交付物 = 工作流 skill(流程)+ 元技能(流程里两处判断)+ 工具脚本(三个自动化步骤)。定性要**拆到成分**,别说「都有一点」。

## 部署模式对定性的影响

| 制品 | D0 | D1 | D2 追加 |
|---|---|---|---|
| 工具脚本 | 脚本 + 输入输出约定 | + 审批/只读/脱敏 + 测试记录 | + 运行手册/回滚/监控/审计/owner |
| 工作流 skill | 线性步骤 + 状态文件 | + 沙盒/权限/证据步骤 | + 变更/灰度/回滚/运行 SOP |
| 元技能 | 判断纪律 | + 控制边界判断 | + 准入/审计/合规判断 |
| SOP 文档 | 人工步骤 | + 测试环境/脱敏 | + 发布/回滚/监控/incident |

**定性结论必须写**:制品类型 + 部署模式 + 运行/回滚/证据件是否齐。缺运行/回滚/证据件 = D1,不是 D2。

## 本 skill 的定性(示范)

fde-48h-sprint 自身是**元技能**:它不固化任何一条具体流程,而是固化「怎么辨真伪、怎么分区约束、怎么定性制品」的**判断纪律**(铁律 + 判别程序 + 回退规则)。但它的 Phase 7-9 会**生产**工作流 skill 和工具脚本——元技能是「造 skill 的 skill」。

## 反例(别这样定性)

- 把固定流程写成元技能:加了十条铁律但流程一成不变 → 过度设计,砍。
- 把含判断的事塞进纯工作流:判断被写成 if-else 硬编码 → 判断丢失,升元技能。
- 把一次性脚本当 skill:没有复用场景 → 就是工具脚本,别封装。
