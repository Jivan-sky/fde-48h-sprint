# Plan 交付后:持续跟进(轻监控)

> 人说完「按 plan 继续开发」或「拿 demo 做业务落地化」后使用。定位:**本 skill 是导航,不是教练——报偏航,不指挥踩油门。** 只保证后续设计不走偏,不干预业务细节。

## 三种跟进模式

| 触发 | 模式 | 盯什么 |
|---|---|---|
| 人:「按 plan 继续开发」 | 开发跟进 | 实做 vs 图谱/三区/制品定性是否一致 |
| 人:「拿 demo 做业务落地化」 | 落地跟进 | 落地改动是否越过硬约束/鉴权/交付边界 |
| 人:「准备进生产/已经上线」 | 生产跟进 | 变更/灰度/回滚/审计/运行是否按 plan 与客户制度执行 |

三种模式用同一套走偏信号,只是所处阶段不同。

## 轻监控三原则

1. **只盯走偏信号,不盯实现细节**:不点评代码风格、语言选择、UI 细节、字段命名——那些不决定偏不偏。
2. **业务细节以现场实际为准,人拍板**:落地中发现 plan 与现场不符,把差异摆出来问人;不强行按 plan 纠现场,也不擅自改 plan。
3. **监控输出 = 一句话**:「没走偏,继续」或「走偏了:plan 第 X 节,建议回 G X / Phase X」——不是打分、不是评审报告。

## 走偏信号清单(唯一要盯的九类)

1. 校验红线全量任一命中;
2. 硬约束被改、或新约束没进三区;
3. 实做与图谱不一致(做了图谱外的东西 / 图谱内节点没实现);
4. 制品定性漂移(说好工具脚本,做成平台);
5. 验证不是一线本人原话;
6. 凭证/鉴权/控制面被绕过(借账号、绕审批、直连未批准端点)。
7. 生产变更无审批/无变更号/无回滚。
8. 数据边界漂移(生产数据进个人设备/外部模型/日志;测试数据混生产)。
9. 模型/Prompt/RAG/评测漂移(未锁版本、索引未重建、未回归、线上手改、指标跌破)。

出现任一条 → 停,报偏航 + 回对应门/Phase;一条不出现 → 继续,闭嘴。

## 明确不管的清单(不指手画脚)

- 代码风格/命名/语言/框架选择;
- 实现步骤的顺序与内部排期(人自己排);
- 业务规则细节(以现场实际为准,人说了算);
- plan 没写的业务字段,按现场补,不算走偏。

## Plan 持续跟进(迭代机制)

1. 每次迭代(新切片/验证结果/新约束)→ 回 plan 更新:三区表、图谱、换单口径,并写「Plan 变更记录」(时间/内容/原因/谁定的)。
2. `<PLAN_HOME>/<项目名>/planbook-state.md` 始终与 plan 同步;下次开工先读 plan 现状 + 变更记录,从最新版继续。
3. 重大变更(硬约束/交付形式/制品定性)→ 回 G4/G5 重新过目。
4. 每次迭代后审三区「假设」:被验证推翻 → 回 Phase 5-6 重规划。
5. D2 上线后按客户监控周期看:成功率/质量/成本/延迟/漂移/审计告警;异常 → 回 G6b 或回滚。
6. 任何生产变更必须能对上变更号/审批/回滚/证据;对不上 = 走偏。

## 一句话纪律

报偏航,不指挥;给选择,不拍板;plan 活着,不止一次交付。
