# 样例计划书：XX MCN 直播复盘 48h MVP（v4 骨架）

> 这是 fde-48h-sprint **v4.6** 的成品样例，演示完整链路：读需求文档 → 判客户层与一号位 → 采矿 + 问题模型 → 辨真伪（Echo 甄别）→ 接口/数据/环境勘测 + 可追溯/回滚预判 → 流程隐患 → 三区 → 计划书 → POC → 48h MVP → 三重验收。内容基于假设需求文档《MCN 运营数字化提效需求》（`样例输入-需求文档.md`），出处标在括号里。

> 本样例走**路线 A（FDE 交付）**、**D0 开放演示**、**M0 MVP**。路线 B（ANC 架构）的差异只在四处：进入时读 ANC、Phase 1 用 Project/DRI/IC/Task 词汇、Phase 10 多查树干接线、Phase 11 落回树干——见 `references/anc-context.md`。

## 0 一句话结论

**真需求；客户层 = 降本增效型；一号位 = 老板（待确认）；部署模式 = D0；当前阶段 = M0；交付形式 = F1 48h 薄切片。** 文档喊的是「建个统一数据平台」，但采矿挖出的真痛点是「运营每天 18 点手工整理 4 个平台数据，凑成一张日报发老板群」——谁拍板是老板，谁在用是运营 3 人。主机会点：把「整理日报」这个每天约 40 分钟的手工动作做成薄切片。**本切片只读导出 + 本地处理，不写入客户任何系统；因此写前基线「不适用（只读）」。**

## 1 需求拆解

- 表面需求（对方说的）：「建一个统一的直播数据平台，打通快手 / 抖音 / 视频号，自动汇总成看板」——§1。
- 细节点：
  - 谁在用：运营每天整理数据（§3.2）
  - 什么动作：手工导出 → 逐条复制粘贴 → 凑成日报（§3.2）
  - 什么数据：直播场次、时长、GMV、UV、订单数、退款数，后台可导 CSV（§2.1）
  - 什么频率：每天 18:00 前（§3.2）
  - 什么事故：上个月两次数据对不上被客户投诉（§4.1）
  - 已有尝试：**文档未提及，待确认**（Phase 3 必问：之前是否上过工具、为什么废了）
- 被推翻的：「统一数据平台 / 三平台看板」不是本切片范围——那是 MCN 管理系统，违反反平台生死线，砍。

## 2 客户分层与一号位

- 客户层：**降本增效型（约 30 人）**。依据：运营团队 3 人（§3.1），管理层诉求是「减少手工整理时间」（§4.2）——要的是**省钱、快速回本、快速验证**，不是组织变革。
- 一号位：老板（文档 §1「管理层要求」，拍板人与收日报人一致）。状态：**待确认**——需核实当前对接人能否直接拍板范围与验收。
- 打法（降本增效层）：**ROI 切单**——聚焦高频痛点（每天），固定范围与报价，验收标准清晰；研发走**轻量工具化**，必须快、稳、上手无学习成本。不铺平台，不讲战略愿景。

## 3 问题模型（五要素，带状态）

- **核心瓶颈**：运营每天要手工把 3 个平台数据搬进一张日报里。状态：**假设**（文档支持动作存在，耗时未实测）。
- **因果链**（≥3 条）：
  1. 平台各自独立、无统一入口（§2.2）——**技术**
  2. 日报要人工逐条复制粘贴（§3.2）——**流程**
  3. 3 个人扛全部汇总，无校验环节（§3.1、§3.2）——**能力 / 流程**
- **量化影响**：每天 18:00 前必发（§3.2）；上月 2 次投诉（§4.1）。**耗时与人力成本未实测，标「未验证」**——老板口径「把时间花在分析上」（§4.2）属定性，不作数字。
- **相关方地图**：主裁 / 收日报人 = 管理层（§4.2）；盟友 = 运营 3 人（§3.1，直接受益）；阻碍者——未识别，待确认。
- **已有尝试**：文档未提及，**尚未验证**；Phase 3 必问（不问 = 可能把失败过的方案再做一遍）。

> Echo 的产出物就是问题模型。访谈只给**证据**，老板口播只给**假设**——本节每条都标了状态。

## 4 真伪辨别

- 谁拍板：老板（§1「管理层要求」、收日报，§4.2）。谁在用：运营 3 人（§3.1、§3.2）。
- Echo 甄别：文档由需求方/管理口径提供，情绪词堆叠（「统一、标准化、提效赋能」，§1），**偏向甲方式拆需求**；若对接人是销售，须补答 E 组后再采信其判断。
- 判断：**真**。证据链：
  - 痛点有实体动作（§3.2 每天手工整理）—— L2（文档陈述，未现场复核）
  - 有事故锚点（§4.1 两次投诉）—— L2
  - 数据源真实存在（§2.1 后台可导出 CSV）—— L2（格式截图未拿到，待确认）
  - 唯一弱证据：没写「整理一次几分钟、几个人」→ **待确认**，Phase 3 必问
  - 未闭合项：是否有过失败尝试—— **L3，不得写成结论**

## 5 机会点提炼（文档采矿）

- 机会点 1：**每天手工整理日报 → 拖单出日报**。证据：§3.2「手工从后台导出后逐条复制」+ §4.1「因数据错漏收到客户投诉 2 次」。
- 机会点 2：**数据对不上返工 → 自动核对**。证据：§4.1 投诉「对不上」；但没写具体对哪几个字段、错在哪一步 → **证据中等，Phase 3 确认**。
- 机会点 3（待确认）：文档写了「老板要看趋势」（§1）但没写谁负责做趋势分析 → 标「文档未提及，待确认」，**不脑补、不进正文建议**。

## 8 重规划决策（三区）

- **硬约束（不可动）**：
  - 不写入快手/抖音/视频号后台；只读导出（业务硬约束，老板/运营确认）。
  - 不自动向老板群/客户发送消息（对外副作用，人工执行）。
  - 客户数据不出演示机/本地，不进外部模型（控制类硬约束，需客户确认）。
- **假设（未验证）**：
  - 运营每天整理约 40 分钟（文档隐含，未实测）。
  - CSV 字段稳定、可直接映射。
  - 一线愿意用「拖 CSV 出日报」而不是继续手工。
- **决策（可改）**：
  - 本切片只做快手单平台；抖音/视频号放 M1。
  - 输出 markdown，不直接发群；是否接 IM 由客户在 M1 决定。
- **最小必要控制集**：只读导出 + 本地处理 + 人工确认后发送；不做账号托管、不做自动发送、不做生产写入。控制成本：低。
- **重规划结果**：平台建设节点砍掉；自动发送节点保留为人工；单平台日报进入 MVP。

## 9 交付物核心能力（薄切片五要素 + 端到端）

- 切片名：拖单出日报（把快手后台导出文件拖进去，自动出日报表格）。
- 输入：快手商家后台导出的 CSV（场次 / 时长 / GMV / UV / 订单数 / 退款数，§2.1 与后台字段一致）。
- 输出：当场出一页可发老板群的日报 markdown（带环比，和昨日差多少）。
- 验证话术：「我 40 分钟的手工活，你 1 分钟出完了，真能帮我」——运营小王，拿她自己后台导出的真实单据当场验证。
- 明确不做：不做抖音 / 视频号接入、不做看板、不做趋势预测、不做管理后台、不做统一数据平台、不自动发消息、不写客户系统。
- 端到端本人：输入自己找运营要、脚本自己写、验证自己跑；不外包、不转包、不等人。
- 制品定性：**工具脚本**（无复杂判断、纯确定性转换）；M0 不封装 skill，M1 若跨场景复用再评估 F5。

## 11 控制面与写前基线

- 部署模式与理由：**D0 开放演示**——只用客户批准的脱敏/样本 CSV，在演示机本地处理；不接客户生产 API，不写客户系统。
- 数据边界：L2 经营数据；只落演示机本地临时目录；不进外部模型；不跨境；验证后按约定删除。
- 权限与 SoD：本切片无客户系统写权限；导出由运营本人完成；FDE 不借用运营账号。
- 变更与发布：本切片不发布到客户生产；M1 起按客户变更制度。
- 审计：保留输入样本来源、处理时间、输出文件哈希、验证记录；不记录账号/Token。
- **写前基线：不适用（只读）**。若 M1 要写客户系统，必须按 `references/write-safety.md` 重新做基线快照/回滚/演练，并重过 G4/G6。
- 写路径控制：本切片无写入；输出文件由人工确认后使用。
- 外部副作用：不自动发消息；日报由运营人工发送。
- 证据索引：见附录 B。

## 12 经济账

- 公式：`净节省工时 × 人力单位成本 × 10-20%`
- 算账：运营 3 人每天各约 40 分钟 = 每天 2 人时 × 22 天 = 44 人时/月；按运营人力成本 30 元/人时 → 月省 1320 元；取 15% 保守系数 → **月价值约 198 元，年约 2400 元**。
- 数字来源：30 元/人时**待确认**（文档未写薪资）；40 分钟/天是文档 §3.2 隐含（「每日 18:00 前需发出」），不是实测 → 两项都要 Phase 3 向运营确认。老板口径「把时间花在分析上」（§4.2）属定性，不折算成金额。
- 控制成本：M0 极低（无写入、无自动发送、无客户系统权限）；主要是验证与人工确认时间。
- 运行成本：M0 为本地脚本，无模型/API/存储成本；M1 若接 IM/云，另算。
- 非裁员价值（至少写一条）：错误返工下降（对照 §4.1 的 2 次投诉）、日报发出时间提前、释放的时间转去做分析（§4.2 明确诉求）。**不替老板制定裁员计划。**
- 结论：**值得做（M0 验证口径）**。单看账不大，但 48h 成本一次；验证过升级 F3/F5 后价值随换单累加。

## 13 验证、验收与后续

- 价值验收：运营小王，拿她当天后台导出的真实 CSV，当场拖进去出日报，她说「能帮到我」（原话记录）。
- 控制验收：M0 无写入、无自动发送、数据不出演示机；客户确认数据边界即可。M1 起补安全/IT 签字。
- 运行验收：M0 由 FDE 现场运行；M1 起明确 owner、监控、告警、人工兜底。
- POC 一页纸：范围 = 快手单平台日报；使用者 = 运营 3 人；成功指标 = 对照今日实测耗时与差错；双方负责人待定；时间 = 48h；**不成功即到点停**；达标后下一阶段 = M1 字段容错/批量，或 M2 小范围试用。
- 沉淀路径（路线 A）：问题模型更新（耗时假设是否被推翻 / 是否查清「已有尝试」）→ 踩坑与脚本 → 写回知识库 / Skill。只放共享盘不算沉淀。
- 换单口径：验证过 → 下一个切片从一线问的「那抖音能不能也这样」里挑；验证不过 → 换切面（如改做自动核对），不硬续。
- 诚实条款：未摸到的字段（逐条）——整理一次精确耗时、人力成本单价、快手后台导出格式截图、**是否有过失败尝试**；均已标「待确认」。L3 线索（只列不作结论）——需求文档「统一、标准化、提效赋能」是管理口径话术；是否有内部推动者、是否有前任试过同类工具——**未闭合，不得写进结论**。
